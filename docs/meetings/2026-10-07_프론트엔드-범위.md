## 요약

프론트엔드를 전부 구현하지 않습니다. 기능지도의 우선순위대로 **실제로 동작하는 기능 6개, 프로토타입 2개, 슬라이드 6개**로 나눕니다. 화면 구성은 프론트엔드 담당(이의진)이 정합니다.

## POC와 프로토타입

| | POC (개념 증명) | 프로토타입 |
|---|---|---|
| 답하는 질문 | "이게 기술적으로 되나?" | "이게 어떤 모습이고 어떻게 쓰나?" |
| 생김새 | 투박해도 됨 | 그럴듯해야 함 |
| 데이터 | 진짜 데이터 | 가짜 데이터여도 됨 |

과제 평가 항목(VectorDB, 청킹, Workflow)은 POC 쪽에 있으므로, 핵심 기능은 진짜로 돌아가야 합니다.

## 프론트와 백엔드 사이 약속 (안)

세 사람이 동시에 작업하려면 아래 형식을 먼저 확정해야 합니다. 프론트는 이 형식의 가짜 응답으로 먼저 만들 수 있습니다.

| 기능 | 요청 | 응답 |
|---|---|---|
| 05·06 찾기 | `question`, `history` | `answer`, `candidates[{series_id, abs_ep?}]`, `follow_up?`, `sources[]` |
| 07 시청처 | `series_id` | `seasons[{name, providers[], checked_at}]` |
| 09 복습 | `series_id`, `seen_ep`, `mode`(요약/인물/마지막 화/직접), `question?` | `answer`, `seen_ep`, `sources[{text, abs_ep, url, license}]` |
| 13 기록장 | `series_id`, `seen_ep`, `rating?` | 저장 결과 |

- `seen_ep`는 필수 인자입니다. 없으면 검색하지 않고 "어디까지 봤어요?"를 되묻습니다.

## 기술 선택 (이의진 결정)

| 안 | 장점 | 단점 |
|---|---|---|
| Streamlit | 파이썬 하나로 백엔드와 바로 연결, 채팅 UI 기본 제공, 6일 안에 가능 | 디자인 자유도가 낮음 |
| HTML/JS + FastAPI | 보기 좋고 기능지도 디자인을 살리기 쉬움 | API 서버를 따로 만들어야 해서 일이 늘어남 |

- 프론트엔드 담당이 정합니다. 백엔드(강권재)와는 연결 방식만 맞추면 됩니다.

## 역할 분담 (안)

한 사람이 한 영역을 끝까지 맡습니다.

| 담당 | 맡을 일 | 결과물 |
|---|---|---|
| 한태호 | 데이터 점검 피드백 반영(정제 버그, 작품 연결 오류) + 필요한 데이터 추가 수집. **끝나면 의진의 프론트엔드를 도움** | 정제된 청크 데이터 (데모 3작품 우선) |
| 이의진 | 프론트엔드 전부: 화면 구성·기술 선택, 실제 동작 기능의 화면, 프로토타입 2개 | 데모 화면 |
| 강권재 | 에이전트 관련 기능 전부: 임베딩, 검색(스포일러 필터), Agent, 평가 | 위 약속대로 동작하는 백엔드 함수 |

- 태호 → 권재: 정제된 청크를 넘기면 권재가 임베딩합니다. 그 전까지 권재는 지금 있는 청크로 검색·Agent를 먼저 만듭니다.
- 의진 ↔ 권재: 위 "프론트와 백엔드 사이 약속" 형식으로 연결합니다. 의진은 그 형식의 가짜 응답으로 화면을 먼저 만듭니다.
- 태호의 데이터 작업은 데모 3작품(귀멸·나히아·진격) 먼저, 10/9까지를 목표로 합니다.
