# 에이전트 대화 설계 (2026-10-11)

- 작성: 강권재
- 목적: 사용자가 모드(찾기·복습·시청처…)를 고르지 않아도 한 문장을 보내면 **에이전트가 기능을 스스로 고르고, 모자라면 되묻는** 입구 `POST /api/chat`를 만든다. 지금은 화면의 모드 칩이 기능을 고르고 사용자가 그 칩을 눌러야 한다.
- 시청 여정 단계: 특정 단계가 아니라 **모든 기능의 입구**(API 서버 설계와 같음). 기능 자체는 기존 `service.py`의 함수를 그대로 쓴다.
- 기준 문서: `docs/design/2026-10-10_API-서버-설계.md`(응답을 그대로 전달, 가짜 모드, 어긋남 방지 테스트), `AGENTS.md` 원칙 2·3(스포일러 차단, 근거 없는 답 금지).

## 성공 기준

1. "히어로 아카데미아 11화까지 봤어" 한 문장으로 작품을 찾아 기록을 저장하고, 다음 할 일(복습·사전)을 제안한다. 사용자는 모드를 고르지 않는다.
2. 도구가 되물으면(`follow_up`) 에이전트가 그 질문을 그대로 사용자에게 한다. 지어내지 않는다.
3. 한 턴에 도구 호출은 최대 3번. 넘으면 지금까지의 결과로 답한다.
4. 응답에 진행 단계(`steps`)가 들어가 의진의 화면이 "시청 기록 확인 중…" 같은 표시를 그대로 보여 줄 수 있다.
5. `make api FAKE=1`에서도 DB·LLM 없이 같은 형식으로 동작한다. `make test`가 DB·LLM 없이 통과한다.

## 결정 사항 (브레인스토밍에서 확정)

| 항목 | 결정 | 이유 |
|---|---|---|
| 방식 | **B. 짧은 도구 루프** — OpenAI function calling으로 LLM이 도구를 고르고, 결과를 보고 다시 고른다. 최대 3번 | 한 턴에 "작품 찾기 → 기록 저장"처럼 두 단계가 자연스럽게 이어진다. 라우터 한 번(A)은 되묻기 뒤 이어가기가 어렵고, 긴 자율 루프(C)는 비용·지연·오답 위험이 크다 |
| 쓰기 권한 | **1. 저장은 바로, 삭제는 안 함** — 사용자가 회차를 말하면 `save_record`를 바로 부른다. `delete_record`는 도구에 없다. `rating`은 사용자가 점수를 말했을 때만 넘긴다 | 저장은 덮어쓰기라 되돌릴 수 있고, 매번 확인을 받으면 대화가 늘어진다. 삭제는 되돌릴 수 없으므로 화면의 기록장 버튼(`DELETE /api/records/{id}`)에만 둔다 |
| 상태 | 서버는 상태 없음. 화면이 `history`를 보낸다 | 지금 `POST /api/find`와 같은 방식. 세션 저장은 범위 밖 |
| 다음 행동 제안 | LLM이 아니라 **마지막 도구에 따른 규칙**으로 정한다 | 결정적이라 테스트할 수 있고, 화면 칩 문구가 흔들리지 않는다 |

## 구조

```
aniwhere/agent/chat.py          ← 새 파일. 도구 목록·단계 문구·루프·제안 규칙. 판단은 전부 여기
aniwhere/agent/prompts/chat.md  ← 시스템 프롬프트
aniwhere/agent/llm.py           ← LLM.tools(...) 메서드 추가 (function calling 1회 호출)
aniwhere/service.py             ← chat(message, history) 추가. 도구 이름 → 자기 함수 연결만 함
aniwhere/api/main.py            ← POST /api/chat. 판단 로직 없음
aniwhere/api/fake.py            ← fake.chat: 낱말 규칙으로 단계·결과 재현
tests/test_app.py, tests/test_api.py
```

의존 방향은 `agent/chat.py → (service가 넘겨 준 호출 함수)`로, `agent`가 `service`를 import하지 않는다. `service.chat`이 "도구 이름 → `service`의 함수"를 잇는 `call(name, args)` 함수를 만들어 `agent.chat.run(...)`에 넘긴다. `api/`는 `svc.chat(message, history)`를 부르고 결과를 그대로 보낸다.

### `LLM.tools` (llm.py)

```python
def tools(self, system: str, messages: list[dict], tools: list[dict], *, allow_tools=True) -> dict:
    """function calling 1회. → {content: str | None, tool_calls: [{id, name, arguments: dict}]}
    allow_tools=False면 tool_choice="none"으로 글만 받음(루프 마무리용). arguments가 JSON이 아니면 {}."""
```

- `messages`는 OpenAI 형식(`{"role": "user"|"assistant"|"tool", ...}`) 그대로. 시스템 메시지는 `system`으로 따로 받는다(기존 `text`·`json`과 같은 모양).
- `temperature` 재시도 로직은 기존 `_chat`과 같다(`_chat`을 `messages`를 받게 넓혀 셋이 공유).
- 키가 없으면 `get_llm()`이 `None`인 것은 그대로.

### 루프 (`agent/chat.py`)

```python
MAX_TOOL_CALLS = 3

def run(llm, message: str, history: list[dict] | None, call) -> dict:
    """call(name, args) → dict. 도구가 ValueError를 내면 call이 아니라 run이 잡는다."""
```

1. `llm`이 `None`이면 도구를 돌리지 않고 `{"answer": None, "follow_up": NEED_LLM, "steps": [], "results": {}, "suggestions": []}`. `NEED_LLM`은 `recommend.py`와 같은 글: ".env에 OPENAI_API_KEY를 넣어 주세요."로 끝나는 안내.
2. `messages` = `history`(`{role, content}`, 최대 20턴 — 넘으면 API가 422로 막으므로 여기서는 자르지 않음) + `{"role": "user", "content": message}`.
3. `llm.tools(prompt("chat"), messages, TOOLS)` 호출.
   - `tool_calls`가 없으면 `content`가 답. 끝.
   - 있으면 **순서대로** 실행한다. 지금까지 실행한 도구가 3개가 되면 남은 호출은 실행하지 않고 `{"error": "이번 턴의 도구 호출 한도(3번)를 넘었습니다. 지금까지의 결과로 답하세요."}`를 그 호출의 결과로 돌려준다.
   - 각 호출: `call(name, args)` → 결과 dict를 `json.dumps(ensure_ascii=False)`로 `tool` 메시지에 넣는다. `ValueError`(모르는 작품 `UnknownSeries` 포함, 회차·평점 범위 밖)는 잡아서 `{"error": str(e)}`를 돌려주고 `steps`에 `ok: false`로 적는다. 다른 예외는 그대로 올린다(500).
   - 결과가 `follow_up`을 가지면(값이 비어 있지 않으면) 기억해 둔다.
4. 3개를 다 썼으면 `allow_tools=False`로 한 번 더 불러 글만 받는다. 아니면 3으로 돌아간다. LLM 호출은 턴당 최대 4번(도구 3번 + 마무리 1번).
5. 응답 조립:
   - `answer`: 이번 턴 **마지막 LLM 응답**의 `content`. 비어 있으면 마지막 성공한 도구 결과의 `answer`(있을 때), 그것도 없으면 `"지금은 답을 만들지 못했어요. 다시 한번 말해 주세요."`.
   - `follow_up`: **마지막으로 실행한 도구**의 결과에 `follow_up`이 있으면 그 글, 없으면 `None`. LLM이 되묻는 글을 바꿔 쓰더라도 화면은 이 값을 믿을 수 있다.
   - `steps`: 실행한 순서대로 `[{tool, label, ok}]`. 한도 초과로 실행하지 않은 호출은 넣지 않는다.
   - `results`: `{도구이름: 그 도구가 돌려준 dict}` — LLM에 보낸 것과 같은 형태(`list`는 `{"items": [...]}`, `get_record`의 `None`은 `{"record": null}`). 실패한 호출은 넣지 않는다. 같은 도구를 두 번 불렀으면 마지막 결과만 남는다.
   - `suggestions`: 아래 규칙표.

### 도구

`TOOLS`는 `chat.py`에 손으로 적은 OpenAI 도구 스키마(`{"type": "function", "function": {name, description, parameters}}`) 목록이다. 설명이 LLM의 선택을 좌우하므로 자동 생성하지 않는다. `LABELS`는 도구 이름 → 화면 문구.

| 도구 | `service` 함수 | 매개변수 | 화면 문구 (`LABELS`) |
|---|---|---|---|
| `search_series` | `search_series(query, limit=5)` | `query: str` | 작품 찾는 중 |
| `list_records` | `list_records()` | 없음 | 시청 기록 확인 중 |
| `get_record` | `get_record(series_id)` | `series_id: str` | 시청 기록 확인 중 |
| `save_record` | `save_record(series_id, seen_ep, rating)` | `series_id: str`, `seen_ep: int`, `rating?: number` | 시청 기록 저장 중 |
| `find` | `find(question, history)` — `history`는 `service.chat`이 끼워 넣음 | `question: str` | 장면으로 작품·회차 찾는 중 |
| `review` | `review(series_id, seen_ep, mode, question)` | `series_id: str`, `mode: summary\|characters\|last\|ask`, `seen_ep?: int`, `question?: str` | 본 회차까지 복습 준비 중 |
| `dictionary` | `dictionary(series_id, seen_ep)` | `series_id: str`, `seen_ep?: int` | 인물·용어 찾는 중 |
| `where_to_watch` | `where_to_watch(series_id)` | `series_id: str` | 시청처 확인 중 |
| `recommend` | `recommend(likes)` | `likes: str` | 취향 분석 중 |

- `delete_record`는 없다. `series`(작품 상세)도 없다 — `search_series` 결과에 이름·전체 회차가 있고, 상세는 화면이 카드로 그릴 때 `GET /api/series/{id}`로 가져온다.
- `get_record`가 `None`을 돌려주면 도구 결과는 `{"record": null}`로 감싸서 보낸다(JSON `null` 하나만 보내지 않기 위해). 나머지 도구는 dict·list를 그대로 보낸다(list는 `{"items": [...]}`로 감싼다).
- `find`에 넘기는 `history`는 `service.chat`이 받은 `history`를 그대로 넘긴다(`agent/find.py`가 `role == "user"`인 턴만 단서로 쓴다).

### 프롬프트 규칙 (`prompts/chat.md`)

시스템 프롬프트에 적는 규칙. 한국어로, 사용자에게는 존댓말.

1. 사용자의 한 문장에서 할 일을 고르고, 필요한 도구를 **먼저** 부른다. 도구 없이 아는 척 답하지 않는다.
2. **도구 결과에 없는 내용은 말하지 않는다.** 작품 이름·회차·시청처·인물 설명은 모두 도구 결과에서 가져온다.
3. `series_id`는 **도구 결과에서만** 가져온다. 기억이나 추측으로 만들지 않는다. 작품 이름만 알면 `search_series`로 먼저 찾는다.
4. 사용자가 "N화까지 봤어"처럼 본 회차를 말하면 `search_series` → `save_record`로 **바로 저장**한다. 확인을 묻지 않는다. 회차 숫자는 사용자가 말한 그대로 넘긴다(시즌 환산 금지). 점수(`rating`)는 사용자가 "4점"처럼 말했을 때만 넘긴다. 저장 뒤에는 저장된 작품명·회차를 한 줄로 알려 준다.
5. 도구 결과에 `follow_up`이 있으면 **그 질문을 그대로** 사용자에게 한다. 다른 도구를 더 부르지 않는다.
6. 도구 결과가 `{"error": ...}`면 그 메시지를 읽고 고친다(예: 모르는 `series_id` → `search_series`로 다시 찾기). 두 번 실패하면 사용자에게 상황을 알린다.
7. 장면 묘사("키 작은 아저씨가 칼 들고…")는 `find`, "어디서 봐"는 `where_to_watch`, "복습"·"지금까지 줄거리"는 `review`, "누구야"·"그 용어 뭐야"는 `dictionary`, "뭐 볼까"·"추천"은 `recommend`, "내 기록"은 `list_records`.
8. 답은 두세 문장. 도구 결과의 목록(후보·출처·시청처)은 화면이 카드로 그리니 글로 되풀이하지 않는다.

### 다음 행동 제안 (`suggestions`) 규칙

마지막으로 **성공한** 도구 기준. 도구를 하나도 부르지 않았거나 모두 실패했으면 `[]`. 그 도구 결과에 `follow_up`이 있으면(되묻는 중) 도구가 무엇이든 `[]`. 그 다음에 아래 표.

| 마지막 도구 | 조건 | `suggestions` |
|---|---|---|
| `find` | `status == "episode"` | `["여기까지 봤어요", "시청처 보기"]` |
| `find` | `status == "series"` | `["이 작품이 맞아요", "시청처 보기"]` |
| `find` | `ambiguous` / `none` | `[]` (`follow_up`이 있으므로 위 규칙에 걸림) |
| `save_record` | | `["3분 복습", "인물 사전"]` |
| `review` | | `["인물 사전", "다음 회차 시청처"]` |
| `dictionary` | | `["3분 복습", "시청처 보기"]` |
| `where_to_watch` | | `["여기까지 봤어요"]` |
| `recommend` | `picks`가 있을 때 | `["시청처 보기", "다른 추천"]`; 없으면 `[]` |
| `search_series`, `list_records`, `get_record` | | `[]` |

칩 문구는 의진의 `app.js`에 이미 있는 것(`'3분 복습'`, `'시청처 보기'`, `'이 작품이 맞아요'`)을 그대로 쓴다. 칩을 누르면 화면은 그 문구를 다음 `message`로 보낸다 — 서버가 따로 해석하지 않는다.

## 엔드포인트

| 기능 | 메서드·경로 | 요청 | 호출 | 응답 |
|---|---|---|---|---|
| 에이전트 대화 | `POST /api/chat` | `{message, history?: [{role, content}]}` | `chat(message, history)` | `{answer, follow_up?, steps[{tool, label, ok}], results{…}, suggestions[]}` |

- `ChatRequest(message=TEXT, history: list[Turn] = [], max 20)` — `FindRequest`와 같은 제한(글 1~1000자, 턴 20개).
- 응답은 `service.chat`의 dict를 **그대로** 보낸다. `service.chat`의 독스트링에 `→ {answer, follow_up?, steps[{tool, label, ok}], results{}, suggestions[]}`를 적어 기존 어긋남 방지 테스트가 `fake.chat`에도 같은 키를 강제하게 한다.
- 기존 엔드포인트(`/api/find`, `/api/review`, …)는 그대로 둔다. 화면의 기록장·카드 상세는 그쪽을 쓴다.

## 오류 처리

| 상황 | 처리 |
|---|---|
| `message` 비었거나 1000자 초과, `history` 21턴 이상 | 422 (pydantic) |
| LLM 키 없음 | 200, `answer: null`, `follow_up: NEED_LLM`, `steps: []`. 도구는 돌리지 않는다 |
| 도구가 `ValueError`(모르는 작품 포함) | 200. LLM에 `{"error": 메시지}`를 돌려주고 `steps[].ok = false`. LLM이 고치거나 사용자에게 알린다. **404·400으로 바꾸지 않는다** — 되묻기가 에이전트의 일이다 |
| 도구가 그 외 예외(DB 끊김 등) | 500 (FastAPI 기본) |
| 도구 호출 4번째 이상 | 실행하지 않고 한도 초과 `error`를 돌려준 뒤 `allow_tools=False`로 마무리 |
| LLM이 모르는 도구 이름을 부름 | `{"error": "없는 도구입니다: <이름>"}`를 돌려주고 `steps`에는 넣지 않는다 |
| LLM `arguments`가 JSON이 아니거나 필수 값 누락 | `call`이 `TypeError`를 내면 `run`이 `ValueError`처럼 다뤄 `{"error": ...}`로 돌려준다 |
| LLM 호출 자체가 실패(네트워크·한도) | 예외 그대로 → 500. 재시도는 `openai` 클라이언트의 `max_retries=2`에 맡긴다 |

## 가짜 모드 (`fake.chat`)

LLM 없이 낱말 규칙으로 `steps`·`results`·`suggestions`를 만든다. 의진이 진행 표시와 칩을 모두 만들어 볼 수 있어야 한다. 규칙은 위에서부터 먼저 맞는 것 하나.

| 메시지에 있는 낱말 | 재현하는 흐름 |
|---|---|
| `봤어` + 숫자 | `search_series` → `save_record(HERO, 숫자)` (fake의 `_records`에 실제로 저장). 답 "「나의 히어로 아카데미아」 N화까지 본 것으로 저장했어요." 제안 `["3분 복습", "인물 사전"]`. 숫자가 범위 밖이면 실제 모드처럼 `save_record` 단계 `ok: false`, 답은 그 `ValueError` 메시지, 제안 `[]` |
| `어디서` | `where_to_watch(HERO)` |
| `복습` 또는 `줄거리` | `get_record(HERO)` → `review(HERO, mode="summary")` |
| `누구` 또는 `용어` | `get_record(HERO)` → `dictionary(HERO)` |
| `추천` | `recommend(메시지)` |
| `기록` | `list_records()` |
| 그 외 | `find(메시지, history)` — 기존 fake `find`의 낱말 규칙(`헷갈`/`없는`/`작품`)이 그대로 네 갈래를 만든다 |

`steps`의 `label`은 `agent/chat.py`의 `LABELS`를 import해서 쓴다(문구가 둘로 갈라지지 않게). `suggestions`는 같은 규칙 함수 `agent.chat.suggest(tool, result)`를 import해서 쓴다. `api/fake.py → agent/chat.py` import는 의존 방향(`agent → api`) 안이다.

## 테스트

DB·LLM·모델 없이 돈다(`tests/test_app.py`는 기존처럼 테스트 DB가 있을 때만).

### `tests/test_app.py` (DB 픽스처 + 대본 있는 FakeLLM)

`FakeLLM`에 `tools(system, messages, tools, allow_tools=True)`를 추가한다. 대본은 호출 순서대로 돌려줄 `{content, tool_calls}` 목록. 받은 `messages`·`tools`를 `calls`에 모아 둔다.

1. **회차 말하면 저장** — 대본: `search_series("A")` → `save_record(A, 11)` → 글. `records.get(db, A).seen_ep == 11`, `steps == [search 작품 찾는 중 ok, save 시청 기록 저장 중 ok]`, `results["save_record"]["seen_ep"] == 11`, `suggestions == ["3분 복습", "인물 사전"]`.
2. **지어낸 `series_id`는 error로 돌아가고 다시 찾음** — 대본: `where_to_watch("tmdb:0")` → `search_series` → `where_to_watch(A)`. 첫 단계 `ok False`, 두 번째 LLM 호출의 마지막 `tool` 메시지에 `"error"`가 있음, 최종 `results["where_to_watch"]`는 A.
3. **도구 3번 상한** — 대본이 `list_records`를 5번 부르게 함. 실행은 3번(`steps` 길이 3), 4·5번째의 `tool` 메시지에는 한도 초과 `error`, 마지막 LLM 호출은 `allow_tools=False`, LLM 호출 수는 총 4 이하.
4. **`follow_up`은 도구 것 그대로** — 대본: `review(A, mode="ask")`(question 없음) → 글. 응답 `follow_up == "무엇이 궁금한지 알려 주세요."`, 되묻는 중이므로 `suggestions == []`.
5. **`rating`은 말했을 때만** — 대본: `save_record(A, 11)`(rating 없음). 저장된 `rating is None`. (프롬프트 규칙은 LLM 몫이지만, `run`이 `rating`을 지어 넣지 않는지 확인.)
6. **키 없으면 되묻기** — `run(None, ...)` → `answer None`, `follow_up`에 `OPENAI_API_KEY`, `steps == []`, `call`이 한 번도 불리지 않음.
7. **도구 목록** — `{t["function"]["name"] for t in TOOLS}`에 `delete_record`가 없고, 모든 이름이 `service.py`의 공개 함수 이름이고, `LABELS`가 모든 도구를 덮는다.
8. **`find`에 `history` 전달** — `service.chat("...", history=[...])`가 `find`를 부를 때 같은 `history`를 넘기는지(`service._find.find`를 monkeypatch).

## 검증 흐름 (구축 방식)

API 서버와 같다: 구현 에이전트가 테스트 먼저 → 검토 에이전트가 규칙 검토(`api/`·`service.py`에 판단 로직 없음, `agent/chat.py`가 `service`를 import하지 않음, 도구에 `delete_record` 없음, 비밀 값 없음, `make test` 통과) → 강권재가 실제 DB·키로 실행.

실제 실행 확인(PR 본문에 출력 그대로):

1. `make api` → `POST /api/chat {"message": "히어로 아카데미아 11화까지 봤어"}` → `steps`에 `search_series`·`save_record`, `GET /api/records/tmdb:65930` → `seen_ep 11`.
2. `POST /api/chat {"message": "그거 어디서 봐?", "history": [위 두 턴]}` → `where_to_watch`.
3. `POST /api/chat {"message": "복습 좀"}` → `review` 또는 `follow_up`(기록이 있으니 `review`).
4. `make api FAKE=1` → 같은 세 요청이 LLM 없이 같은 키로 응답.
