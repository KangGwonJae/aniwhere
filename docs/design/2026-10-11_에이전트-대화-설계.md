# 에이전트 대화 설계 (2026-10-11)

- 작성: 강권재
- 목적: 사용자가 모드(찾기·복습·시청처…)를 고르지 않아도 한 문장을 보내면 **에이전트가 기능을 스스로 고르고, 모자라면 되묻는** 입구 `POST /api/chat`를 만든다. 지금은 화면의 모드 칩이 기능을 고르고 사용자가 그 칩을 눌러야 한다.
- 시청 여정 단계: 특정 단계가 아니라 **모든 기능의 입구**(API 서버 설계와 같음). 기능 자체는 기존 `service.py`의 함수를 그대로 쓴다.
- 기준 문서: `docs/design/2026-10-10_API-서버-설계.md`(응답을 그대로 전달, 가짜 모드, 어긋남 방지 테스트), `AGENTS.md` 원칙 2·3(스포일러 차단, 근거 없는 답 금지).
- 검토: 초안을 세 관점(화면 소비자·LLM 도구 호출 운영·코드베이스 적합성)의 검토 에이전트가 봤고, 그 결과를 반영했다. 판정은 맨 끝 "검토 반영" 절.

## 성공 기준

1. "히어로 아카데미아 11화까지 봤어" 한 문장으로 작품을 찾아 기록을 저장하고, 다음 할 일(복습·사전)을 제안한다. 사용자는 모드를 고르지 않는다.
2. 도구가 되물으면(`follow_up`) 그 질문이 **글자 그대로** 사용자에게 간다. 에이전트가 지어내지 않는다.
3. 한 턴에 도구 호출은 최대 3번, LLM 호출은 최대 4번. 넘으면 지금까지의 결과로 답한다.
4. 응답에 실행한 단계(`steps`)가 들어가 화면이 답과 함께 "어떤 단계를 거쳤는지" 보여 줄 수 있다. **실시간 진행 표시는 아니다**(응답이 끝난 뒤 한꺼번에 온다). 기다리는 동안 화면은 자체 문구를 쓴다.
5. 다음 행동 칩을 누르면 그 자체로 완전한 문장이 서버로 가서, 이전 턴을 기억하지 못하는 서버에서도 바르게 동작한다.
6. 스포일러 범위는 **기록장 값만** 쓴다. 대화 경로에서 LLM이 범위를 늘릴 수 없다.
7. `make api FAKE=1`에서도 DB·LLM 없이 같은 형식으로 동작하고, 칩 흐름까지 만들어 볼 수 있다. `make test`가 DB·LLM 없이 통과한다.

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 방식 | **B. 짧은 도구 루프** — OpenAI function calling으로 LLM이 도구를 고르고, 결과를 보고 다시 고른다. 한 턴에 도구 3번 | 한 턴에 "작품 찾기 → 기록 저장"처럼 두 단계가 자연스럽게 이어진다. 라우터 한 번(A)은 되묻기 뒤 이어가기가 어렵고, 긴 자율 루프(C)는 비용·지연·오답 위험이 크다 |
| 쓰기 권한 | **1. 저장은 바로, 삭제는 안 함** — 사용자가 회차를 말하면 `save_record`를 바로 부른다. `delete_record`는 도구에 없다. `rating`은 사용자가 점수를 말했을 때만 | 저장은 덮어쓰기이고 이전 값을 답에 적어 주므로 사용자가 바로 되돌릴 수 있다. 삭제는 되돌릴 수 없으므로 화면의 기록장 버튼(`DELETE /api/records/{id}`)에만 둔다 |
| 저장 보호 | 프롬프트만 믿지 않는다. `series_id` 출처, 회차 숫자, 평점, 시즌 표기를 **코드가** 검사한다(아래 "save_record 보호") | 기록은 다른 모든 기능의 스포일러 기준이다. 잘못 저장되면 복습·사전이 모두 틀어진다 |
| 상태 | 서버는 상태 없음. 화면이 `history`를 보내고, 각 assistant 턴에 서버가 준 `context`를 붙여 되돌려 준다 | 지금 `POST /api/find`와 같은 방식. 세션 저장은 범위 밖. `context`가 없으면 "그거 어디서 봐?" 같은 이어 말하기가 불가능하다(검토 지적) |
| 되묻기 | 도구 결과에 `follow_up`이 있으면 **루프를 바로 끝내고** 그 글을 답으로 쓴다. LLM을 다시 부르지 않는다 | 질문이 원문 그대로 나가는 것을 코드가 보장한다. LLM 호출 1번을 아낀다 |
| 다음 행동 제안 | LLM이 아니라 **마지막으로 성공한 도구에 따른 규칙**. 칩은 `{label, message}` — `message`는 서버가 채운 완전한 문장 | 결정적이라 테스트할 수 있고, 상태 없는 서버에서도 칩이 동작하며, 가짜 모드의 낱말 규칙에도 걸린다 |

## 구조

```
aniwhere/agent/chat.py          ← 새 파일. TOOLS·LABELS·run()·suggest()·as_result()·save_record 보호. 판단은 전부 여기
aniwhere/agent/prompts/chat.md  ← 시스템 프롬프트
aniwhere/agent/llm.py           ← _chat이 message 객체를 돌려주게 넓히고 LLM.tools(...) 추가
aniwhere/service.py             ← chat(message, history) 추가. {도구이름: 자기 함수} dict를 run()에 넘기기만 함
aniwhere/api/main.py            ← POST /api/chat. 판단 로직 없음
aniwhere/api/fake.py            ← fake.chat: 낱말 규칙으로 단계·결과 재현. LABELS·suggest·as_result는 agent/chat.py에서 import
tests/test_chat.py(새, DB 없음), tests/test_llm.py(새), tests/test_app.py, tests/test_api.py
```

의존 방향: `agent/chat.py`는 `service`를 import하지 않는다. `service.chat`이 `{"search_series": search_series, …}` dict를 만들어 `agent.chat.run(llm, message, history, fns)`에 넘긴다. `api/fake.py → agent/chat.py` import는 `agent → api` 방향 안이다(ARCHITECTURE.md: "api는 agent를 호출하고 결과만 전달"). `agent/chat.py`가 import하는 `llm.py`·`config`는 DB·모델을 불러오지 않으므로 `make api FAKE=1`은 그대로 가볍다.

`service.chat`에는 연결만 있다:

```python
def chat(message: str, history: list[dict] | None = None) -> dict:
    """→ {answer, follow_up?, steps[{tool, label, ok, args}], results{}, suggestions[{label, message}], context?}"""
    history = history or []
    fns = {"search_series": search_series, "list_records": list_records, "get_record": get_record,
           "save_record": save_record, "find": find, "review": review, "dictionary": dictionary,
           "where_to_watch": where_to_watch, "recommend": recommend, "series": series}
    return _chat.run(get_llm(), message, history, fns)
```

`series`는 LLM 도구가 아니다. `run`이 칩 문장·`context`에 넣을 제목을 찾을 때만 내부에서 쓴다. `fns`의 값은 **공개 `service` 함수만**(모두 `_plain`을 거쳐 JSON으로 바꿀 수 있다). `agent`·`records` 모듈을 직접 넣지 않는다.

### `LLM.tools` (llm.py)

```python
def _chat(self, messages: list[dict], **extra):   # → openai message 객체 (content, tool_calls 포함)
def text(self, system, user) -> str                # _chat(...).content or ""
def json(self, system, user) -> dict
def tools(self, system: str, messages: list[dict], tools: list[dict], *, allow_tools=True) -> dict:
    """function calling 1회. → {content: str | None,
         tool_calls: [{id, name, arguments: dict}],   # arguments가 JSON이 아니면 {}
         raw: dict}                                   # 다음 요청에 그대로 붙일 assistant 메시지(OpenAI 형식)
    allow_tools=False면 tool_choice="none"(tools는 그대로 보냄). parallel_tool_calls=False."""
```

- `raw`는 `message.model_dump(exclude_none=True)`에서 `role`·`content`·`tool_calls`만 남긴 dict. `tool_calls[].function.arguments`는 **원문 문자열**(파싱 실패 시 `"{}"`), `type == "function"`이 아닌 호출은 버린다.
- `tools()`에는 `response_format`을 넣지 않는다. `temperature` 재시도는 기존 `_chat`과 같다. `parallel_tool_calls`를 받지 않는 모델이면 `temperature`와 같은 자리에서 그 인자만 빼고 다시 부른다.
- 키가 없으면 `get_llm()`이 `None`인 것은 그대로.

### 루프 (`agent/chat.py`)

```python
MAX_TOOL_CALLS = 3           # LLM이 낸 tool_call 개수. 실행·실패·모르는 도구 모두 센다
MAX_LLM_CALLS = MAX_TOOL_CALLS + 1
NEED_LLM = "에이전트 대화에는 LLM이 필요해요. .env에 OPENAI_API_KEY를 넣어 주세요."   # chat.py 자기 상수

def run(llm, message: str, history: list[dict], fns: dict) -> dict:
```

1. `llm`이 `None`이면 도구를 돌리지 않고 `{"answer": NEED_LLM, "follow_up": NEED_LLM, "steps": [], "results": {}, "suggestions": [], "context": None}`.
2. OpenAI `messages`를 만든다. `history`의 각 턴은 `{"role", "content"}`로 넣되, assistant 턴에 `context`가 있으면 `content` 끝에 한 줄을 붙인다: `"\n[직전 결과: tool=find, series_id=tmdb:65930, 제목=나의 히어로 아카데미아, 회차=49]"`. 마지막에 `{"role": "user", "content": message}`.
3. `llm.tools(prompt("chat"), messages, TOOLS)` 호출. LLM 호출 수를 센다.
   - `tool_calls`가 없으면 `content`가 답. 끝.
   - 있으면 **`raw`를 `messages`에 먼저 붙이고**, 호출을 순서대로 처리한다. 모든 `tool_call_id`마다 `{"role": "tool", "tool_call_id": id, "content": json.dumps(결과, ensure_ascii=False)}`를 **정확히 하나씩** 붙인다(실행·한도 초과·모르는 도구·인자 오류 모두). 빠지면 다음 요청이 400으로 실패한다.
   - 각 호출의 처리 순서:
     1. 누적 `tool_call` 수가 `MAX_TOOL_CALLS`를 넘으면 실행하지 않고 `{"error": "이번 턴의 도구 호출 한도(3번)를 넘었습니다. 지금까지의 결과로 답하세요."}`. `steps`에 넣지 않는다.
     2. `TOOLS`에 없는 이름이면 `{"error": "없는 도구입니다: <이름>"}`. `steps`에 넣지 않는다.
     3. 인자를 스키마의 `properties`에 있는 키만 남기고 버린다(`user_id`·`limit`·`history` 따위를 LLM이 넣어도 무시). 필수 키가 빠졌으면 `{"error": "<키>가 필요합니다"}`, `steps`에 `ok: false`.
     4. `save_record`면 아래 "보호" 검사. 실패하면 `{"error": …}`, `steps`에 `ok: false`.
     5. `find`면 LLM 인자를 쓰지 않고 `fns["find"](message, find_history)`를 부른다(아래 "find").
     6. `fns[name](**args)` 실행 → `as_result(값)`. `ValueError`(모르는 작품 `UnknownSeries` 포함, 회차·평점 범위 밖, 잘못된 `mode`)는 잡아서 `{"error": str(e)}`, `steps`에 `ok: false`. 다른 예외는 그대로 올린다(500).
     7. 성공하면 `steps`에 `{tool, label, ok: true, args}`, `results[name] = 결과`.
     8. 결과에 `follow_up`이 있으면(비어 있지 않으면) **루프를 끝낸다**. 남은 호출에는 `{"error": "되묻는 중이라 실행하지 않았습니다"}`를 붙이고 5로 간다. `answer = follow_up`.
   - LLM에 보내는 결과는 `slim(결과)`: `sources[].text`·`debug`를 뺀 것. 화면용 `results`는 뺀 것 없이 그대로.
4. 누적 `tool_call` 수가 한도에 닿았거나 LLM 호출 수가 `MAX_LLM_CALLS - 1`이면 `allow_tools=False`로 한 번 더 불러 글만 받는다. 아니면 3으로 돌아간다. 어떤 경로로도 LLM 호출은 4번을 넘지 않는다.
5. 응답 조립:
   - `answer`: 되묻는 중이면 `follow_up`. 아니면 이번 턴 마지막 LLM 응답의 `content`. 비어 있으면 고정 문구 `"지금은 답을 만들지 못했어요. 다시 한번 말해 주세요."`. 도구의 긴 `answer`(복습 본문)는 폴백에 쓰지 않는다 — `results`에만 있다.
   - `save_record`가 성공했으면 코드가 만든 확인 문장을 `answer` **앞에** 붙인다: `"「{name}」 {seen_ep}화까지로 저장했어요."` 이전 기록이 있었으면 `"(이전 {previous_seen_ep}화)"`를 덧붙인다. LLM이 "저장했어요"라고 말해도 실제 저장은 이 문장이 있을 때만이다.
   - `follow_up`: 되묻는 중이면 그 글, 아니면 `None`.
   - `steps`: 실행한 순서대로 `[{tool, label, ok, args}]`. `args`는 걸러낸 뒤의 인자(`find`는 `{}`).
   - `results`: `{도구이름: as_result(값)}`. 실패한 호출은 넣지 않는다. 같은 도구를 두 번 불렀으면 마지막 성공 결과만 남는다.
   - `context`: 마지막으로 성공한 도구 기준 `{tool, series_id?, title?, seen_ep?}`. 성공한 도구가 없으면 `None`. 값의 출처는 아래 표.
   - `suggestions`: 아래 규칙.

### `as_result`

도구 함수가 돌려준 값을 JSON 객체 하나로 만든다. dict는 그대로, list는 `{"items": [...]}`, `None`은 `{"record": null}`. `fake.chat`도 같은 함수를 쓴다.

### `context` 값의 출처

| 마지막 성공 도구 | `series_id` | `title` | `seen_ep` |
|---|---|---|---|
| `find` | `candidates[0].series_id` (status가 episode·series일 때) | `candidates[0].title` | `candidates[0].abs_ep` (episode일 때) |
| `save_record`, `get_record`(기록 있음) | 결과 `series_id` | 결과 `name` | 결과 `seen_ep` |
| `review`, `dictionary`, `where_to_watch` | `args.series_id` | 이번 턴 `results`에서 찾고, 없으면 `fns["series"](id)["title_ko"]`(없으면 `title`) | 결과 `seen_ep`(review·dictionary) |
| `search_series` | 결과가 **정확히 1건**일 때만 그 `series_id` | 그 `name` | 없음 |
| `recommend` | `picks[0].series_id` (있을 때) | `picks[0].title` | 없음 |
| `list_records` | 없음 (`{tool}`만) | | |

### 도구

`TOOLS`는 `chat.py`에 손으로 적은 OpenAI 도구 스키마 목록이다. 설명이 LLM의 선택을 좌우하므로 자동 생성하지 않는다. `LABELS`는 도구 이름 → 화면 문구(말줄임표 없음, 화면이 `…`를 붙인다).

| 도구 | `service` 함수 호출 | LLM이 넘기는 매개변수 | `LABELS` |
|---|---|---|---|
| `search_series` | `search_series(query, limit=5)` | `query: str` | 작품 찾는 중 |
| `list_records` | `list_records()` | 없음 | 시청 기록 확인 중 |
| `get_record` | `get_record(series_id)` | `series_id: str` | 시청 기록 확인 중 |
| `save_record` | `save_record(series_id, seen_ep, rating)` | `series_id: str`, `seen_ep: int`, `rating?: number` | 시청 기록 저장 중 |
| `find` | `find(message, find_history)` — LLM 인자는 쓰지 않음 | 없음 | 장면으로 작품·회차 찾는 중 |
| `review` | `review(series_id, None, mode, question)` — `seen_ep`는 늘 `None`(기록장 값) | `series_id: str`, `mode: summary\|characters\|last\|ask`, `question?: str` | 본 회차까지 복습 준비 중 |
| `dictionary` | `dictionary(series_id, None)` — `seen_ep`는 늘 `None` | `series_id: str` | 인물·용어 찾는 중 |
| `where_to_watch` | `where_to_watch(series_id)` | `series_id: str` | 시청처 확인 중 |
| `recommend` | `recommend(likes)` | `likes: str` | 취향 분석 중 |

- `delete_record`는 없다. `series`는 LLM에 보이지 않는다(내부 조회용).
- **`review`·`dictionary`의 스키마에 `seen_ep`가 없다.** 두 함수는 `seen_ep=None`이면 기록장을 읽고, 기록이 없으면 `follow_up`(어디까지 봤는지)으로 되묻는다. 사용자가 새 회차를 말하면 `save_record`를 먼저 거치므로 저장된 값이 그대로 범위가 된다. LLM이 `seen_ep`를 넘겨도 3단계에서 버려진다. (초안에는 `seen_ep?`가 있었다 — 기록이 11화일 때 LLM이 12를 넣으면 `dictionary`는 자르지 않고 12화까지 검색해 스포일러가 새는 길이었다.)
- **`find`**: `question`은 사용자 원문 `message`(LLM이 바꿔 쓰면 근거가 바뀐다). `find_history`는 `history`의 **마지막 assistant 턴의 `context.tool == "find"`일 때만** `history` 전체, 아니면 `[]`. `agent/find.py`는 `role == "user"`인 턴을 모두 단서로 이어 붙이므로, 찾기와 관계없는 대화("11화까지 봤어", "추천해 줘")가 섞이면 결과가 틀어진다.

### `save_record` 보호 (코드)

`run`이 실행 전에 검사한다. 하나라도 걸리면 실행하지 않고 `{"error": …}`를 LLM에 돌려준다(LLM이 되묻거나 고친다).

| 검사 | 통과 조건 | 오류 글 |
|---|---|---|
| `series_id` 출처 | 이번 턴의 성공한 결과에 나온 id(`search_series.items[].series_id`, `find.candidates[].series_id`, `get_record`·`list_records`의 `series_id`) 또는 `history[*].context.series_id` 가운데 하나 | `series_id는 search_series 결과나 직전 결과에서 가져오세요` |
| 후보 모호 | 이번 턴 `search_series`가 2건 이상이고 그중 하나를 고른 경우, 고른 작품의 `name` 또는 `title`이 `message`에 들어 있어야 함(띄어쓰기·기호·대소문자 무시: "테스트칼날" = "테스트 칼날"). `find`·`get_record`·`list_records`·`context`에서 온 id는 이 검사를 건너뜀 | `후보가 여러 개입니다. 어느 작품인지 사용자에게 물으세요` |
| 회차 숫자 | `str(seen_ep)`가 `message`의 **저장 가능 숫자**에 있어야 함. 저장 가능 숫자 = `message`에 "N화까지"가 있으면 그 N들만("7화까지 봤는데 8화 내용 알려줘"의 8은 질문), 없으면 글의 모든 아라비아 숫자. 직전 턴이 작품을 되물은 상태(마지막 assistant 턴의 `context`가 없거나 `tool == "search_series"`)면 그 앞 user 턴의 숫자도 인정("테스트 7화까지 봤어" → "어느 작품?" → "테스트 칼날"). 부정·가정·질문형을 완전히 막지는 못하며 프롬프트 규칙과 함께 쓴다 | `사용자가 말한 회차 숫자만 저장할 수 있어요` |
| 시즌 표기 | `message`에 `\d+\s*(기|시즌|season|쿨)` 또는 `(시즌|season)\s*\d+`이 있으면 거절("3기 11화", "시즌 3 11화", "2쿨") | `시즌 안 회차는 저장하지 않아요. 전체 기준으로 몇 화인지 물으세요` |
| 평점 | `rating`은 `str(rating)`(또는 정수형)이 `message`에서 `점` 바로 앞 또는 `별` 바로 뒤에 있을 때만 넘긴다("4점", "4.5점", "별 4개". "별로였어"의 별, "11화"의 1은 아님). 아니면 `rating=None`으로 바꿔 부른다(거절하지 않음) | 없음 |

- 회차가 **줄어드는** 저장(24 → 11)은 허용한다. 사용자가 고치는 경우가 있다. 대신 실행 전에 `fns["get_record"](id)`로 이전 값을 읽어 결과에 `previous_seen_ep`·`previous_rating`을 넣고, 확인 문장에 "(이전 24화)"를 붙여 바로 되돌릴 수 있게 한다. 이 `get_record` 호출은 한도에 세지 않고 `steps`에도 넣지 않는다.
- 한 턴에 저장은 **한 작품만**(프롬프트 규칙). 두 번째 `save_record`는 코드가 `{"error": "한 턴에 한 작품만 저장해요. 나머지는 다음에 말해 달라고 하세요"}`로 거절한다.

### 프롬프트 규칙 (`prompts/chat.md`)

시스템 프롬프트에 적는 규칙. 한국어로, 사용자에게는 존댓말. 코드가 지키는 규칙도 LLM이 알아야 헛된 호출을 줄이므로 함께 적는다.

1. 사용자의 한 문장에서 할 일을 고르고, 필요한 도구를 **먼저** 부른다. 도구 없이 아는 척 답하지 않는다. 도구는 한 번에 하나씩 부른다.
2. **도구 결과에 없는 내용은 말하지 않는다.** 작품 이름·회차·시청처·인물 설명은 모두 도구 결과에서 가져온다.
3. `series_id`는 **도구 결과나 `[직전 결과: …]` 줄에서만** 가져온다. 추측으로 만들지 않는다. 작품 이름만 알면 `search_series`로 먼저 찾는다. 후보가 여럿이고 사용자가 말한 이름과 정확히 맞는 것이 없으면 어느 작품인지 묻는다.
4. 사용자가 "N화까지 봤어"처럼 **봤다고 단정한** 문장이면 `search_series` → `save_record`로 바로 저장한다. 확인을 묻지 않는다. 부정·미래·가정·질문형("아직 안 봤어", "보면 알려 줘", "11화가 뭐였지")은 저장하지 않는다. 회차 숫자는 사용자가 말한 그대로, 시즌 표기("3기 11화")면 전체 기준으로 몇 화인지 묻는다. 점수는 사용자가 "4점"·"별 넷"처럼 말했을 때만 `rating`에 넣는다. 한 턴에 한 작품만 저장한다.
5. 저장과 함께 다른 요청이 있으면("11화까지 봤는데 지금까지 줄거리 알려 줘") 저장 뒤 그 요청도 처리한다. **본 회차 다음 내용은 물어도 말하지 않는다.**
6. 도구 결과에 `follow_up`이 있으면 그 질문이 사용자에게 간다. 더 할 일은 없다(코드가 멈춘다).
7. 도구 결과가 `{"error": …}`면 그 메시지를 읽고 고친다(예: 모르는 `series_id` → `search_series`로 다시 찾기). 두 번 실패하면 사용자에게 상황을 알린다.
8. 장면 묘사("키 작은 아저씨가 칼 들고…")는 `find`, "어디서 봐"는 `where_to_watch`, "복습"·"지금까지 줄거리"는 `review`, "누구야"·"그 용어 뭐야"·"인물·용어"는 `dictionary`, "뭐 볼까"·"추천"은 `recommend`, "내 기록"은 `list_records`. 복습·사전의 범위는 기록장이 정한다 — 회차를 지정할 수 없다.
9. 답은 두세 문장. 도구 결과의 목록(후보·출처·시청처)은 화면이 카드로 그리니 글로 되풀이하지 않는다. 다만 **작품 이름과 회차는 글에 넣는다**(다음 턴의 단서가 된다).

### 다음 행동 제안 (`suggestions`) 규칙

마지막으로 **성공한** 도구 기준. 성공한 도구가 없거나 되묻는 중(`follow_up` 있음)이면 `[]`. 칩은 `{"label": 화면 글, "message": 서버가 채운 완전한 문장}`. 화면은 `label`을 보여 주고, 누르면 `message`를 다음 `message`로 보낸다. 서버는 칩을 따로 해석하지 않는다. `{제목}`은 `context.title`, 없으면 그 칩을 뺀다.

| 마지막 도구 | 조건 | `label` → `message` |
|---|---|---|
| `find` | `status == "episode"` | `여기까지 봤어요` → `{제목} {abs_ep}화까지 봤어` / `시청처 보기` → `{제목} 어디서 볼 수 있어?` |
| `find` | `status == "series"` | `시청처 보기` → `{제목} 어디서 볼 수 있어?` / `인물·용어` → `{제목} 인물·용어 알려줘` |
| `save_record` | | `3분 복습` → `{제목} 지금까지 복습해줘` / `인물·용어` → `{제목} 인물·용어 알려줘` |
| `review` | | `인물·용어` → `{제목} 인물·용어 알려줘` / `시청처 보기` → `{제목} 어디서 볼 수 있어?` |
| `dictionary` | | `3분 복습` → `{제목} 지금까지 복습해줘` / `시청처 보기` → `{제목} 어디서 볼 수 있어?` |
| `where_to_watch` | | `3분 복습` → `{제목} 지금까지 복습해줘` / `인물·용어` → `{제목} 인물·용어 알려줘` |
| `recommend` | `picks`가 있을 때 | `시청처 보기` → `{picks[0].title} 어디서 볼 수 있어?` / `다른 추천` → `다른 작품도 추천해줘` |
| `search_series`, `list_records`, `get_record` | | `[]` |

`label` 가운데 `3분 복습`·`시청처 보기`·`여기까지 봤어요`는 의진의 `app.js`에 이미 있는 문구다. `인물·용어`는 `index.html`의 모드 칩 문구와 맞췄다(초안의 `인물 사전`은 화면에 없는 문구였다). `다른 추천`은 새 문구다.

`suggest(tool, result, context) -> list[dict]`는 `chat.py`의 순수 함수. `fake.chat`도 이것을 쓴다.

## 엔드포인트

| 기능 | 메서드·경로 | 요청 | 호출 | 응답 |
|---|---|---|---|---|
| 에이전트 대화 | `POST /api/chat` | `{message, history?: [{role, content, context?}]}` | `chat(message, history)` | `{answer, follow_up?, steps[{tool, label, ok, args}], results{}, suggestions[{label, message}], context?}` |

- `ChatTurn(role: Literal["user", "assistant"], content: str(1..2000), context: dict | None = None)`. `role`을 `Literal`로 막는 이유: `"system"`이면 프롬프트를 덮어쓸 수 있고, `"tool"`이면 OpenAI가 400을 내서 500이 된다. 기존 `Turn`(find용)은 그대로 둔다.
- `ChatRequest(message=TEXT, history: list[ChatTurn] = [], max_length=20)`. **history 항목 최대 20개 = 왕복 10번.** 화면은 `history.slice(-20)`으로 보낸다.
- 응답은 `service.chat`의 dict를 **그대로** 보낸다. 독스트링 `→ {…}`로 기존 어긋남 방지 테스트가 `fake.chat`에도 같은 키를 강제한다.
- 기존 엔드포인트(`/api/find`, `/api/review`, `/api/records`…)는 그대로 둔다. 기록장 화면·카드 상세(`GET /api/series/{id}`)는 그쪽을 쓴다.

### 화면 연결 규칙 (의진에게 전달)

- **말풍선** = `answer`. 되묻는 중이면 `answer == follow_up`이므로 둘을 다 띄우지 않는다. `follow_up != null`은 "되묻는 중" 상태 표시(칩 없음)에만 쓴다.
- **history에 넣는 assistant 턴** = `{role: "assistant", content: answer, context: context}`. `context`는 받은 그대로 되돌려 보낸다(화면이 해석하지 않는다).
- **주 카드** = `results[context.tool]`. 도구별 카드: `find` → 후보 카드, `save_record`·`get_record` → 기록 카드, `where_to_watch` → 시청처 서랍, `review` → 복습 서랍(본문은 `results.review.answer`), `dictionary` → 인물·용어 서랍, `recommend` → 추천 카드, `search_series`·`list_records` → 목록. `context`가 `null`이면 카드 없음.
- `steps`는 답과 함께 "거친 단계"로 보여 준다(화면이 `…`를 붙여 빠르게 재생해도 좋다). 기다리는 동안은 화면 자체 문구.
- `answer`·`follow_up`·`label`은 일반 글이다. `textContent`로 넣는다(`innerHTML` 금지 — LLM 답에 `<`가 들어올 수 있다).
- 칩을 누르면 `message`를 그대로 `/api/chat`에 보낸다. 지금 `app.js`의 `send()`가 `'3분 복습'`·`'시청처 보기'`를 가로채 mock 서랍을 여는 부분은 의진이 지우거나, 서랍을 열되 `/api/chat` 응답의 `results`로 채운다(의진 결정).
- 시작 제안 칩(`'인물 관계'` 등)을 `/api/chat`으로 보낼 거면 완전한 문장("인물 관계로 복습해줘")으로 바꾸기를 권한다.

## 오류 처리

| 상황 | 처리 |
|---|---|
| `message` 비었거나 1000자 초과, `history` 21개 이상, `role`이 user·assistant가 아님, history `content` 2000자 초과 | 422 (pydantic) |
| LLM 키 없음 | 200, `answer == follow_up == NEED_LLM`, `steps: []`, `context: null`. 도구는 돌리지 않는다 |
| 도구가 `ValueError`(모르는 작품 포함), 보호 검사 실패, 필수 인자 누락 | 200. LLM에 `{"error": 메시지}`를 돌려주고 `steps[].ok = false`. **404·400으로 바꾸지 않는다** — 되묻기가 에이전트의 일이다 |
| 모르는 도구 이름 | `{"error": "없는 도구입니다: …"}`. `steps`에 넣지 않는다. 한도에는 센다 |
| 도구 호출 한도 초과 | 실행하지 않고 한도 초과 `error`. 모든 `tool_call_id`에 `tool` 메시지는 붙인다 |
| 도구가 그 외 예외(DB 끊김 등), LLM 호출 자체 실패(네트워크·한도) | 500 (FastAPI 기본). 재시도는 `openai` 클라이언트의 `max_retries=2`에 맡긴다 |

이 PR에서는 턴 전체 데드라인을 두지 않는다. 최악의 경우 바깥 LLM 4번 + 도구 안의 LLM(`find` 2번, `review`·`recommend` 1번씩) 호출이 겹쳐 수십 초가 걸릴 수 있다. `follow_up` 즉시 종료와 `slim`으로 줄이되, 데드라인·스트리밍은 범위 밖.

## 가짜 모드 (`fake.chat`)

LLM 없이 낱말 규칙으로 `steps`·`results`·`suggestions`·`context`를 만든다. 의진이 진행 표시·칩·카드를 모두 만들어 볼 수 있어야 하므로, **`suggest()`가 내는 모든 `message`가 아래 규칙에 걸려야 한다**(테스트로 지킨다). 규칙은 위에서부터 먼저 맞는 것 하나. `LABELS`·`suggest`·`as_result`는 `agent/chat.py`에서 import.

| 메시지에 있는 낱말 | 재현하는 흐름 |
|---|---|
| `봤어` + 숫자 | `search_series("히어로")` → `save_record(HERO, 숫자)` (fake의 `_records`에 실제로 저장). 답 "「나의 히어로 아카데미아」 N화까지로 저장했어요." (이전 기록이 있으면 "(이전 M화)"). 숫자가 범위 밖이면 `save_record` 단계 `ok: false`, 답은 그 `ValueError` 메시지, 제안 `[]`, `context`는 `search_series` 기준 |
| `시청처` 또는 `어디서` | `where_to_watch(HERO)` |
| `복습` 또는 `줄거리` | `get_record(HERO)` → `review(HERO, mode="summary")` |
| `인물` 또는 `용어` 또는 `누구` 또는 `사전` | `get_record(HERO)` → `dictionary(HERO)` |
| `추천` | `recommend(메시지)` |
| `기록` | `list_records()` |
| 그 외 | `find(메시지, history)` — 기존 fake `find`의 낱말 규칙(`헷갈`/`없는`/`작품`)이 그대로 네 갈래를 만든다. `ambiguous`·`none`이면 `follow_up`이 있으므로 `answer == follow_up`, 제안 `[]` |

## 테스트

### `tests/test_chat.py` (새 파일, **DB·LLM 없음**)

`run()`을 stub `fns`(dict를 돌려주는 함수들)와 대본 LLM으로 돈다. `ScriptLLM(replies)`: `tools()`가 불릴 때마다 대본의 다음 `{content, tool_calls}`를 돌려주고, 받은 것을 `calls.append({"messages": copy.deepcopy(messages), "tools": tools, "allow_tools": allow_tools})`로 모은다(참조로 두면 `run`이 같은 리스트에 덧붙여서 모두 마지막 상태를 가리킨다). `tools()`는 매 호출마다 **메시지 순서를 검사**한다: `role == "tool"`인 메시지의 `tool_call_id`가 바로 앞 assistant 메시지의 `tool_calls` id에 있고, 그 assistant의 모든 id에 `tool` 메시지가 있어야 한다. 아니면 `AssertionError`.

1. **키 없음** — `run(None, …)` → `answer == follow_up == NEED_LLM`, `steps == []`, stub이 한 번도 불리지 않음.
2. **한 번에 하나씩 5번** — 대본이 `list_records`를 다섯 번 부름. `steps` 길이 3, LLM 호출 4번, 네 번째 `allow_tools is False`.
3. **한 응답에 5개** — 첫 응답에 `tool_calls` 5개. 3개 실행, 다음 호출의 `messages`에 `tool` 메시지 5개, 그중 2개의 `content`에 `"한도"`. LLM 호출 2번.
4. **모르는 도구·인자 누락** — 모르는 이름 3번 → `steps == []`, LLM 호출 4번(한도에 셈). `get_record()`(인자 없음) → `steps[0].ok is False`, `tool` 메시지에 `"series_id"`.
5. **스키마 밖 인자 버림** — 대본이 `get_record(series_id=A, user_id="x")`, `search_series(query="q", limit=9999)` → stub이 받은 kwargs에 `user_id`·`limit` 없음.
6. **`follow_up`이면 즉시 종료** — stub `review`가 `follow_up` 있는 dict → LLM 호출 1번, `answer == follow_up`, `suggestions == []`, `context.tool == "review"`.
7. **`review`·`dictionary`에 `seen_ep` 못 넘김** — 스키마 `properties`에 `seen_ep` 없음. 대본이 `review(series_id=A, mode="summary", seen_ep=99)` → stub이 받은 kwargs에 `seen_ep` 없음(`service`가 `None`으로 부름).
8. **`save_record` 보호** — 각각 한 테스트: 출처 없는 id → error / `search_series` 2건 + 이름 안 맞음 → error / 숫자가 `message`에 없음 → error / "3기 11화" → error / `rating=4`인데 `message`에 "점" 없음 → stub이 받은 `rating is None` / "4점" 있음 → `rating == 4` / 두 번째 저장 → error / 이전 기록 있음 → 결과 `previous_seen_ep`, `answer`가 `"「A」 7화까지로 저장했어요. (이전 3화)"`로 시작.
9. **`find` 인자** — 대본 `find(question="바꿔 쓴 글")` → stub은 `(message, [])`를 받음. history 마지막 assistant `context.tool == "find"`면 `(message, history)`.
10. **`slim`** — `review` 결과에 `sources[].text`가 있어도 다음 LLM 호출의 `tool` 메시지에는 없고, `results.review.sources[0].text`에는 있음.
11. **도구 목록** — `TOOLS` 이름에 `delete_record`·`series` 없음, 모두 `service`의 공개 함수 이름(`inspect`로 `aniwhere.service` 확인), `LABELS`가 모든 도구를 덮음, `review`·`dictionary` 스키마에 `seen_ep` 없음.
12. **`suggest`·`context`** — 표의 갈래마다 기대 `label`·`message`. `title`이 없으면 그 칩이 빠짐. `search_series` 2건이면 `context`에 `series_id` 없음.
13. **`service.chat` 연결** — `monkeypatch.setattr(service, "db", lambda: None)`, `monkeypatch.setattr(service, "get_llm", lambda: ScriptLLM(...))`, `monkeypatch.setattr(service._find, "find", stub)` → `service.chat("…", history)`가 `find`에 `(message, history)`를 넘김. `fns`의 키 집합이 `TOOLS` 이름 + `{"series"}`.

## 검증 흐름 (구축 방식)

API 서버와 같다: 구현 에이전트가 테스트 먼저 → 검토 에이전트가 규칙 검토(`api/`·`service.py`에 판단 로직 없음, `agent/chat.py`가 `service`를 import하지 않음, 도구에 `delete_record` 없음·`review`/`dictionary`에 `seen_ep` 없음, `history.role`이 `Literal`, 비밀 값 없음, `make test` 통과) → 강권재가 실제 DB·키로 실행.

실제 실행 확인(PR 본문에 출력 그대로):

1. `make api` → `POST /api/chat {"message": "히어로 아카데미아 11화까지 봤어"}` → `steps`에 `search_series`·`save_record`, `answer`가 "「나의 히어로 아카데미아」 11화까지로 저장했어요. (이전 49화)"로 시작, `GET /api/records/tmdb:65930` → `seen_ep 11`. 끝나면 `"히어로 아카데미아 49화까지 봤어"`로 되돌린다.
2. 1의 응답에서 `suggestions[1].message`(`… 인물·용어 알려줘`)를 history와 함께 보냄 → `dictionary`, `results.dictionary.seen_ep == 11`.
3. `POST /api/chat {"message": "그거 어디서 봐?", "history": [1의 두 턴(context 포함)]}` → `where_to_watch(tmdb:65930)`.
4. `POST /api/chat {"message": "12화 내용 알려줘"}` → 기록이 11화이므로 12화 내용이 답에 없음(`results.review.seen_ep == 11` 또는 LLM이 거절).
5. `make api FAKE=1` → 1·2·3과 같은 요청이 LLM 없이 같은 키로 응답.
